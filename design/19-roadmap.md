# 19 里程碑路线图、依赖与风险登记册

> **目标**：把 20 份设计变成"可以一步一步做、每步都能独立发布"的施工顺序，并诚实标出规模与风险。
> 本文是所有文档的**总装图**：哪个块挡着哪个块、每个里程碑的验收标准、以及"什么时候算做完"。

---

## 1. 怎么用这份文档

1. 先读 `01`（要做什么）与 `02`（骨架），再按本文件的顺序取块。
2. 每个块的做法：**读该块的设计 → 产出一份机械可执行的 PLAN（模板见仓库根既有 `PLAN.md`）→ 实现 → 过 `check.ps1` → 真机验证 → 更新 README/HANDOFF**。
3. **不许跳步**：没有"设计 → 计划"就直接写代码的块，一律视为未完成（这是本项目已经吃过亏的地方）。
4. 每完成一个块，回来勾掉 §5 的验收项，并把新发现（库行为、服务商策略）写进 `A1` 与 `HANDOFF.md`。

```
M0 库探针 + DB 读池 ──┬─► 03 存储 v3（双库/迁移）──┬─► 04 同步 v2（窗口/配额/进度）

                      ├─► 05 账号与 OAuth2 ──► 06 迁移（账号导入）
                      └─► 02 前端技术栈决策（P1）──► 12 UI 设计系统 ──► 08 阅读/会话串、09 搜索界面、10 规则编辑器

关键路径：M0 → 03 → 04 → 05 → 07 → 08 → 12 → （09/10/11/13/14/15/16 并行可穿插）
硬外部依赖（人）：OAuth 应用注册（05，最慢）、代码签名证书（17）、域名/隐私政策（若走 Google 验证）
```

**可以并行/穿插的块**（互不阻塞）：10 规则、11 通讯录、13 通知细节、14 安全细节、15 性能、17 分发、18 协议扩展。

## 5.5 依赖顺序上的一条硬约束（评审补）
**LDAP/GAL 必须排在 S/MIME 加密之前**（14 §11）：没有目录服务就拿不到收件人证书，S/MIME 加密只能对
"从签名邮件里拿到的证书"生效。若把 S/MIME 加密排在 LDAP 前，等于先做一个**用不了**的功能，
再回头补依赖。M3 的排期按此约束：`CAL/联系人同步 → LDAP/GAL → S/MIME 加密`。

## 9. 路线图自身的红队与验收（模板要求；评审补）

**红队视角（除了 §6 的 R1-R14 风险，还要直面"这份排期本身"的问题）**
1. **"人月"是骗人的单位**：M1a 3-5 人月里，`03` 存储重写与 `12` 前端换栈都是"一天不写就退步"的活；
   真实瓶颈不是编码而是**真机验证**（21 家服务商 × 认证/同步/发信，每家都要账号）。
   缓解：M1a 只承诺"**3 家国内 + 2 家国际**真机通过"，其余走能力快照 + 用户反馈。
2. **单人维护下"完成定义"会自己松掉**：`19` §5 的 DoD 有 8 条，累的时候最先砍的是"文档回写"与"门禁"。
   缓解：把这两条写进**每次提交的检查清单**（`check.ps1` 里已有 fmt/clippy/test，再加"文档改动"这一项只能人工确认）。
3. **M0 的探针可能推翻更多设计**：M0-1/M0-5/M0-6/M0-8 每一项的结论都可能改一个模块。
   缓解：M0 的产出必须包含"**哪些设计因此改了**"的一行记录（A1 的惯例），而不是只留一句"探针通过"。
4. **里程碑之间没有"可发布点"**：M1a 结束时才是第一个能推荐给朋友的版本，中间 3-5 个月没有反馈。
   缓解：M1a 内部按 `04 → 05 → 07 → 12` 切出**四个可自用节点**（自己每天用它收信），先吃自己的狗粮。
