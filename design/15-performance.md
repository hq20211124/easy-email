# 15 性能与大数据量

> **目标**：把"快"变成**可测量、可回归、可降级**的工程指标，而不是口号。
> 10 万封是**验收规模**（不是上限）：冷启动、切文件夹、搜索、滚动、内存、索引吞吐都要有数字。
>
> 覆盖 ID：PERF-01…05、SYN-08（并发预算）、SEC-11（加密对性能的影响，M3）。
> 上游：02（并发模型）、03（存储）、09（索引）。下游：所有功能块（它们都要遵守预算）。

---

## 1. 目标与非目标

**目标**
1. **一套夹具**：可重复生成 10 万封（含正文、附件、中英文、会话串、已读未读分布）的测试邮箱。
2. **一套基准**：`tools/bench.ps1` 一键跑完 **16** 项指标（与 §4 的 P1-P16 一一对应；脚本自己断言条数），输出表格 + 历史曲线。
3. **一套预算**：所有文档里的性能数字汇总到本文（§4），冲突时以本文为准。
4. **降级策略**：预算不达标时先降级（虚拟化、分页、惰性、限速），不允许"让用户忍着"。
5. **内存克制**：常驻 ≤ 300 MB；大附件/大邮件处理时峰值有明确上限与拒绝策略。

**非目标**
- 不追极限吞吐（这是桌面客户端，不是归档服务器）。
- 不为老机器（4 GB 内存、机械盘）做特殊优化，但**降级策略**要保证它能用（列表虚拟化 + 减少预取）。

## 5. SQLite 调优（写进 `DbOptions` 的默认值）

```sql
pragma journal_mode = wal;          -- 读写不互斥（既有）
pragma synchronous = normal;        -- 崩溃丢最后一笔事务，不损坏库（既有）
pragma busy_timeout = 5000;         -- 既有
pragma temp_store = memory;         -- 排序/临时表走内存
pragma cache_size = -65536;         -- 64 MB 页缓存（读池每条连接）
pragma mmap_size = 268435456;       -- 256 MB（按可用内存可调）
pragma page_size = 4096;            -- 建库时定（默认即可）
pragma foreign_keys = off;          -- 我们自己做级联删除（性能更好、语义更可控）
pragma wal_autocheckpoint = 1000;   -- 约 4 MB 触发一次 checkpoint
pragma auto_vacuum = incremental;   -- **必须是第一条 pragma，排在 journal_mode=wal 之前**
                                    --  （M0-7 实测：切 WAL 会写数据库头，之后就静默忽略；建库后再设同样无效）
                                    --  于是 incremental_vacuum 变空操作、配额清理腾不出磁盘）；
                                    --  v1/v2 老库只能靠一次显式全量 VACUUM
```
**工程纪律**
1. **一个事务一批**（500-1000 行）；禁止逐行 autocommit（既有代码的问题）。
2. **预编译语句复用**（`prepare_cached`）用于热点查询（列表/计数/索引写入）。
3. **计数列维护**（未读/总数/会话计数）而不是 `count(*)` 全表扫描；夜检对账（16）。
4. **`ANALYZE`**：迁移后与维护时各跑一次；热点查询计划进基准输出（`EXPLAIN QUERY PLAN` 断言用到的索引）。
5. **`incremental_vacuum`** 配合 `auto_vacuum = incremental`（建库时定）避免全量 VACUUM 停顿。
6. **索引节制**：每个索引都要在基准里对应一条查询；没有消费者的索引删掉（写放大）。
7. **避免 `select *`**（既有代码已无）；列顺序与索引顺序对齐。
8. **FTS 写入批量 + 定期 `optimize`**（维护任务，不在用户操作路径上）。

## 6. 前端性能

| 项 | 做法 |
|---|---|
| 列表 | 虚拟化（视口 ± 8 行）；行高固定/可测；滚动用 `requestAnimationFrame` 批量提交 |
| IPC | 分页 ≤ 200 行；大文本（正文）单独取；事件节流（进度 ≤ 5 次/秒） |
| 首屏 | 骨架屏优先；非首屏模块（设置/规则）动态 import |
| 搜索 | 输入防抖 250 ms；结果分页；高亮在 Rust 侧算（09 §5.2） |
| 主题切换 | 只切 `data-theme` + CSS 变量，不重建 DOM |
| 正文渲染 | iframe 只在打开时创建；切邮件复用同一个 iframe（改 `srcdoc`）而不是重建 |
| 附件预览 | 大文件先取前 N KB 预览（文本）；图片按需缩略 |
| 内存 | 离开阅读态时清空 `detail`（只保留当前一封）；列表行数据是纯值（无 DOM 引用） |

## 7. 内存与句柄（如何采样）

```powershell

[PSCustomObject]@{
  WorkingSetMB = [math]::Round($p.WorkingSet64/1MB,1)

```
- 采样点：启动后 10 s、滚动 30 s 后、搜索 100 次后、收 500 封后、打开 20 封大邮件后、空闲 10 分钟后。

## 10. 门禁新增项

1. **夹具可生成**：`cargo test --test fixture_smoke` 能生成 1 万封夹具并跑完最小基准（≤ 3 分钟）。
2. **预算数字单一来源**：本文的预算表与代码里的常量（如 `MAX_LIST_ROWS`、单封上限、批量大小）一致（脚本比对）。
3. **热点查询有索引**：四条查询计划断言。
4. **无逐行 autocommit**：`db/` 之外的代码不得直接持有 `Connection`（02 的门禁已含）；批量写必须走 `write_batch`。
5. **IPC 载荷**：前端分页请求的 `limit` 不得超过服务端上限（脚本比对常量）。

## 11. 逆向反驳（红队）

**反驳 1：10 万封是"最大规模"还是"典型规模"？为不存在的场景优化是浪费。**
- 证据：国内企业邮箱常见几万封；Gmail 用户十几万封不罕见；而**索引与同步的开销随封数线性增长**，
  我们已经在为"全量窗口同步"做设计（04），所以 10 万封是会真实出现的。
- 缓解：①基准同时跑 1 万（典型）与 10 万（压力）；②降级策略保证 30 万封也能用（只是慢）；
  ③把"体积/内存"作为第一约束（它们比延迟更容易失控）。
- 让步：不为 100 万封设计（那需要放弃单库 SQLite，属于产品级重设计）。

**反驳 2：`.ps1` + 手动跑的基准会被忽略（没人跑就没人管）。**
- 缓解：①CI 里跑宽松版（1 万封）；②`check.ps1` 里加"预算常量一致性"检查（§10.2）；
  ③每个里程碑结束时强制跑一次完整基准并记录（19 §5 的 DoD 里含"性能块要有基准数字"）。
- 让步：接受"完整基准是里程碑级动作，不是每次提交"。

**反驳 3：把 `pragma` 调到 `synchronous=normal` + `mmap` 很大，掉电会不会损坏数据？**
- 证据：WAL + `normal` 的语义是"崩溃可能丢最后一笔已提交事务，但不会损坏数据库"（既有实现已如此）。
  这对**缓存库（cache.db）**没问题；但 `user.db` 里是用户数据（草稿/规则/联系人）。
- **改设计**：`user.db` 用 **`synchronous = full`**（草稿与规则不能因为掉电丢），
  `cache.db` 保持 `normal`（可重建）。这条写进 03 的 `DbOptions` 并按库区分。
- 让步：性能影响（草稿保存变慢）由"本地保存 ≤ 20 ms"的预算吸收（草稿是小事务）。

**反驳 4：虚拟列表 + 键盘导航 + 无障碍三者会互相打架（虚拟化会移除 DOM，破坏焦点与 aria）。**
- 证据：这是真实难点。
- 缓解：①列表容器保持 `role="listbox"`，只渲染视口的 `option`；②**焦点永远在容器**（用 `aria-activedescendant`
  指向当前项），被移除时焦点不丢；③键盘导航由容器统一处理（不依赖 DOM 节点存在）；
  ④屏幕阅读器的 `aria-setsize`/`aria-posinset` 提供总数与位置。
- 让步：如果实测 Narrator 体验不佳，退化为"键盘导航可用 + 禁用虚拟化（≤ 2000 行时）"的双模式。

**反驳 5：把内存预算压到 300 MB 会不会让功能（正文缓存、预览）打折？**
- 证据：300 MB 是"常驻"目标，不是峰值。
- 缓解：①正文以**磁盘**为准（`user.db`/`cache.db`），内存里只留当前打开的正文与最近 20 封的摘要；
  ②预览走临时缓冲并及时释放；③峰值记录在基准里（24 MB 附件 ≤ 3× 已编码邮件）并在设置页显示当前占用。
- 让步：允许在"内存充足的机器"上自动放宽（检测物理内存 ≥ 16 GB 时提高缓存），但**预算数字不变**。
