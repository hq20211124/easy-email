# Easy Email 产品级详细设计 · 设计程序

> **这是什么**：一套分块、可逐块实现的产品设计文档。目标是让 Easy Email 从"能收发的 v0.2"
> 变成"用户愿意从 Outlook / Foxmail / 网易邮箱大师 / Thunderbird 换过来的桌面邮件客户端"。
>
> **怎么用**：
> 1. 先读 [`01-product.md`](01-product.md)（功能全集 + 需拍板的决策），确认范围没有遗漏、决策有结论。
> 2. 再按依赖顺序读 `02 → 19`。每份文档都能独立开发，但**依赖关系不能颠倒**（见 §4 里程碑）。
> 3. 每份文档的 §11「逆向反驳」是红队结论，**实现时不要绕过它**；§12 是必须由人拍板的问题。
> 4. 实现某个块时，把它当作 `PLAN.md` 的输入：本设计给"是什么/为什么/函数长什么样"，
>    实施计划再给"改哪些文件、替换前后的完整代码、逐条验收"。既有 `PLAN.md`
>    （历史回填 + 离线提示）已属于 M1 的一小部分，见 §6。
>
> **语言约定**：文档中文；标识符、代码、DDL、函数签名英文。所有"用户可见文案"写在文档里，
> 实现时直接抄，不要临场发挥。

## 3. 六条红线（任何设计都不得违背）

1. **密码与令牌只进 Windows 凭据管理器 / DPAPI 加密存储**，绝不进 `accounts.json`、日志、缓存库。
   缓存库里出现任何明文凭据 = 一票否决。
2. **邮件正文只在 `iframe sandbox` + 独立 CSP 里渲染，远程内容默认拦截**。
   "好看"不允许以放宽这条为代价（安全策略可以更细，不能更松）。
3. **数据是用户的**：本地缓存可删除、可导出、可重建；任何迁移/清理都不许静默丢邮件；
   "删到服务器"必须是显式动作且有确认。
4. **离线可用**：列表、正文、搜索、写信、草稿、组织操作在断网时都必须能工作；
   联网后自动收敛（发件箱、旗标、草稿）。
5. **失败必须可解释**：任何用户可感知的失败都要有"原因 + 该怎么办"的中文文案，
   不允许把库的错误直接抛给用户（既有 `error.rs` 的传统，继续执行）。
6. **不引入需要我们自己长期运营的服务器**（推送中转、账号后端、遥测后端）。
   本地优先；确实需要的（如 OAuth 应用注册、更新清单托管）用静态托管 + 用户自有凭据解决。
   > 例外需用户明确同意，并在设计中写清运营成本。

## 5. 质量门槛（设计阶段就定死，实现时照做）

- 每个功能块实现前，必须先由本设计产出一份**机械可执行**的实施计划（模板见仓库根 `PLAN.md` 的既有风格：
  完整的前后代码、锚点、逐条验收、预期输出）。
- 每块实现后必须过 `tools/check.ps1`，并把本设计 §10 列出的新不变量加进去
  （这个项目最有价值的传统：**把"容易再犯的错"钉成一条检查**）。
- 每个用户可感知的失败路径都要有测试或明确的人工验收步骤；"没验过"必须写进 `HANDOFF.md`。
- 性能预算（§8）不达标时，先降级（虚拟列表、分页、惰性加载），不允许"用户忍着"。

## 6. 与现有代码/文档的关系

- `README.md`（面向用户与开发者的现状说明）、`HANDOFF.md`（跨会话交接真相）继续维护；
  本设计是**目标态**，三者冲突时以本设计为准，但 `HANDOFF.md` 的"库的坑/环境的坑"优先级最高
  （那是实测结论，不是设想）。
- 已完成的 v0.2 能力（连接池、IDLE 推送、托盘、附件收发、本地缓存与搜索、历史回填计划）
  在 M1 里都是**演进而非重写**；本设计会明确标注"改造 / 保留 / 替换"。
- 仓库根 `PLAN.md`（历史回填 + 离线提示）是 M1 的一个子块，先做它不影响后续设计。
