# DECISIONS —— 决策记录（ADR）

> 每条决策含：**背景 / 选项 / 结论 / 后果**。状态：`已定`（设计阶段已决定）、`待拍板`（需要用户）、
> `待实测`（由基准或探针决定）。

## D1 技术栈：继续 Tauri v2 + Rust（`已定`）
- **背景**：v0.2 已用 Tauri v2 + Rust 跑通收/发/缓存/搜索/推送，且真机验证过。
- **选项**：重写为 Electron/C#；继续 Tauri。
- **结论**：继续。理由：内存/体积优势（对照 D4 的"快、小、不发胖"）、Rust 侧已有 4 千行可信代码、
  WebView2 在 Win10 1803+/Win11 上是系统组件（不用打包 100+ MB 运行时）。
- **后果**：UI 能力受 WebView2 限制（Chromium 154，足够）；需要自己处理 Windows 集成（13/17）。

## D2 前端技术栈：**已定 —— Vite + TypeScript + Svelte 5**（P1，2026-10-03）
- **背景**：现状是单文件 `src/app.js`（47 KB）+ 手写 CSS，无打包器；用户给的硬要求是"**美观 + 极致性能**"。
- **选项**：①无打包器；②Vite + TS + Svelte 5；③React；④Solid。
- **结论**：②。理由：**美观**这条最贵的是"设计系统能否被机械守住"，而 Svelte 把 CSS 当第一等公民
  （scoped style + 编译期样式，令牌单一来源几乎免费）；**性能**这条要的是"长列表里改一行只动一行"，
  编译期生成的细粒度更新（无虚拟 DOM）正合适，运行时 ~10-15 KB，主包可压到 ≤ 300 KB。
  Solid 性能同级但 CSS 与生态更弱；React 的运行时与协调开销与"极致性能"相悖。
- **后果**：①多一条 `npm run build` 与 `node_modules`；②`check.ps1` 的 6 项前端检查必须改造
  （**含"必须自己跑前端构建"，否则会绿着发出旧 UI**）；③**不用 UI 组件库、不用 CSS-in-JS、不用路由库**
  （它们各自带令牌/运行时，会与 `12` 的令牌系统打架）；④若遇生态硬缺口，允许把**单个组件**换成自研
  Web Component（组件契约是框架无关的），不推翻整体选择。

## D3 数据库访问：单写线程 + 读池（`已定`）
- **背景**：现有"每条命令开一条短连接 + 逐行 autocommit"在 10 万封规模下不成立
  （10 万次事务提交），而 `rusqlite::Connection` 是 `!Sync`，跨 `.await` 持有会破坏 `Send`。
- **选项**：①继续按操作开连接；②`tokio::sync::Mutex<Connection>`；③**写线程 + 读池 + 闭包 move 执行**。
- **结论**：③。闭包要求 `'static + Send` 是"跨线程执行"的事实描述，**不是** `pool_op!` 那种
  `for<'a>` 借用约束（`HANDOFF` §3 的坑不会重演）；同时提供具名查询函数覆盖 90% 调用点。
- **后果**：批量写必须走 `write`（事务化）；测试要用 `open_shared_memory`（`:memory:` 多连接各自独立）。

## D4 双库拆分：`cache.db`（可删）与 `user.db`（用户数据）（`已定`）
- **背景**：README 一直教用户"缓存不想要就删"，但草稿、发件箱、规则、联系人、本地标签属于用户数据。
- **选项**：①单库 + 文档警告；②双库（attach）。
- **结论**：②。`user.db` 存 drafts/outbox/**pending_ops**/rules/blocklist/allowlist/contacts/
  contact_emails/saved_searches/search_history/import_jobs/notification_log/kv/signatures/templates；
  `cache.db` 存 folders/messages/bodies/attachments/blobs/threads/FTS/**labels/message_labels**/
  index_queue/sync_jobs/metrics/sent_index/import_dedupe。
- **判据**：用户意图与不可再生的进 `user.db`（**`pending_ops` 是用户意图**：删缓存不该悄悄撤销用户点过的动作）；
  能从服务器/缓存重建的进 `cache.db`。
- **连接方式（评审后改定）**：**两个独立句柄，不做 `ATTACH`**。理由：①`pragma synchronous` 按连接生效，
  ATTACH 后无法一个 `full` 一个 `normal`；②rusqlite 0.40 没有 `attach()` 封装，附着库备份还要
  `new_with_names`；③**实测没有任何写路径需要跨库事务**（跨库的那几处都是幂等的，崩溃后由同步纠正）。
  于是 `user.db` 用 `synchronous=full`、`cache.db` 用 `normal`。
- **实现前置**：备份需要 rusqlite 的 **`backup` feature**（当前 Cargo.toml 只有 `bundled`）。
- **特例**：`accounts.kind ∈ {pop3, local}` 的账号**不写 `pending_ops`**（服务器上无动作可执行）。
- **后果**：备份/vacuum/迁移都要分库（03 §11 反驳 6）；`user.db` 用 `synchronous=full`（15 §11 反驳 3）。

## D5 同步窗口可配 + 配额感知（`已定`）
- **背景**：Gmail IMAP 每天约 2.5 GB 下载、网易企业邮三方默认只给 30 天（A1-F1/F2）。
- **结论**：窗口四档（全部/最近 N 年/最近 N 封/仅按需）+ **每日字节预算账本**（到预算主动停、次日续）
  + 加账号时给体量与时间预估 + 服务端下界提示。
- **后果**：不再承诺"全部同步完成"；UI 只显示"已缓存 X/共 Y"。

## D6 推送模型：IDLE 的 `NewData`（亚秒级）（`已定`，**更正了既有结论**）
- **背景**：`HANDOFF` 声称 async-imap 0.12 不投递 `* n EXISTS`；**实测推翻了它**（A1-F41，约 206 ms 到达）。
- **结论**：以 L1（NewData）为主；保留 L2 心跳（默认 120 s，外层再包硬超时）；L3 轮询兜底。
- **后果**：通知延迟从"最多 50 秒"变成"亚秒级"；实现第 1 步是**在自家夹具上复核**并改掉错误注释/README；
  `tests/library_probe.rs` 把这类库行为变成断言（16 §11 反驳 4）。

## D7 不使用服务器的扩展能力（`已定`）
- **背景**：`THREAD`/`ESEARCH`/`NAMESPACE`/`LIST-STATUS` 在 imap-proto 0.17 里**没有语法**，
  一旦服务器回应就会让整条连接被判为解析失败（A1-F42）。
- **结论**：会话串本地算（08）；排序/复杂条件用 `UID SEARCH` 透传；**永不发**上述命令。
- **后果**：Gmail 的 `X-GM-THRID` 只能通过上游 PR 暴露（可选优化）；服务端"文件夹状态"用逐邮箱 `STATUS`。

## D8 发信：自己组 MIME + `send_raw`（`已定`）
- **背景**：lettre 0.11 的 builder 会重编码（改 CTE、折行、补头），`Body` 是 `Vec<u8>`（不能流式）；
  DSN/BINARYMIME/PIPELINING 都不支持（A1-F45）。
- **结论**：用 `mail-builder` 组 MIME 写入 spool（CRLF 正确）→ `AsyncTransport::send_raw` 发送；
  **不请求 DSN**（只解析收到的退信）；单封上限 `min(服务商上限, 25 MB)`。
- **后果**：峰值内存 ≈ 2× 邮件大小（诚实记录）；要更大附件需自研 SMTP DATA 流式（M3）。

## D9 令牌存储：DPAPI 用户级文件（`已定`）
- **背景**：Windows 凭据管理器 blob 上限 2 560 字节；微软 refresh token 常见 1-4 KB（A1-F35）。
- **结论**：`vault.bin`（`CryptProtectData` + 应用熵，**不用** `CRYPTPROTECT_LOCAL_MACHINE`，传 `NULL` prompt）；
  密码/授权码仍在凭据管理器；轮换式令牌"先写新再删旧"。
- **后果**：诚实披露"挡不住同用户恶意软件"；提供"退出并撤销令牌"。

## D10 Gmail 认证：**已定 —— 不自费 CASA；应用专用密码优先 + BYO client_id；不做内置 ID**（P2，2026-10-03）
- **背景**：Gmail 的 IMAP/POP/SMTP 需要**受限 scope** ⇒ 公开发布绕不开验证 + **每年 CASA**
  （A1-F25 记录的一种价目：AL1 $675 / 带无限复审 $855 / AL2 $5400，Google 本身不收费）。
  未验证应用的硬限制：**终身累计 100 用户、不可重置**；Testing 模式另加 **refresh token 7 天失效**。
- **用户的约束**：**不花一分钱搭建任何东西**。
- **结论**（在此约束下的最优解）：
  1. **默认路径：应用专用密码**（Gmail 仍支持，需两步验证；A1-F39）。用户 2 分钟搞定、不需要建云项目、
     不花钱；我们按 `AuthCode` 轴处理（凭据进 Windows 凭据管理器，与国内授权码同一套代码）。
  2. **进阶路径：BYO client_id**（用户自己建一个 OAuth 客户端）。**Workspace 用户把客户端设为 `Internal`
     即免验证、免 CASA、无警告屏** —— 这是企业用户的干净路径；个人用户建完自己的客户端后
     "发布为生产（未验证）"也不受 7 天限制（只是首次授权会看到"未验证应用"提示，可点"高级→继续"）。
     我们提供分步向导 + 粘贴校验（`client_id`/`tenant`），**不收集、不上传任何东西**。
  3. **不做内置 client_id**：内置就意味着要么每年付 CASA，要么把全体用户塞进"100 人 + 7 天令牌"的牢笼。
  4. **微软照旧内置**（注册免费、无 CASA）：所以"微软账号一键登录、Gmail 需要两步"这个差异要在
     UI 里**如实说明**，并给出"为什么"（一句话：Google 对读邮件范围的第三方客户端收年费）。
- **后果**：①Gmail 用户首次配置比微软多 2-5 分钟（诚实换免费）；②若将来有人赞助 CASA 或项目获得
  已验证客户端，只需把 `OAuthClientRef` 从 `Custom` 翻成 `Bundled`，**架构不用改**；
  ③BYO 向导的"要不要填 `client_secret`"取决于 M0-8 的端点探测结论（A1-F32 记录 Google 官方口径：
  桌面客户端的 secret 不被当作机密）。

## D11 不做 PST / 不做别人的密码库（`已定`，`01` P13/P14）
- **背景**：PST 无纯 Rust 实现、唯一路线许可自相矛盾、New Outlook 已无 MAPI；
  解密别的客户端凭据库与凭据窃取工具无法区分（A1-F6…F9）。
- **结论**：都不做。PST 给"用户自行用第三方工具导出成 mbox/eml 再来导入"的说明页（06 §5.5）。
- **后果**：Outlook 本地存档用户有一段无法自动迁移；用服务器重同步覆盖绝大多数 M365 用户。

## D12 后端抽象 `MailBackend`（`已定`）
- **背景**：将来要接 POP3/JMAP/Graph，不能让同步引擎到处 `use imap::`。
- **结论**：`sync/` 与 `src-tauri` 只依赖 trait；能力位驱动 UI 降级（18 §3）。
- **后果**：POP3 的"没有文件夹/旗标"在 UI 上必须显式降级，不许假装支持。

## D13 索引分词器：**已定 —— CJK 感知的 bigram**（`已定`，2026-10-03，**由实测推翻原基线**）
- **背景**：FTS5 的 `unicode61` 把连续汉字当一个 token（搜"账单"命中 0），`trigram` 需要 ≥3 字符
  （两字中文词搜不到，实测 100k 语料命中 0 行）。
- **原结论（错）**："基线保持逐字符，换不换由基准决定"。
- **实测把它推翻了**（A1-F47）：逐字符**不仅体积大（126.9% vs bigram 的 65.1%），还会误报** ——
  `发\n票`、`developer 发 票 test` 都会命中"发票"（只要两个字之间夹着分隔字节），
  而 HTML 正文里两个相邻汉字之间夹换行/标签是常态。bigram 同时更准、更小、查询延迟相同。
- **结论**：`to_index_text` 与 `to_match_phrase` 共用**同一个** CJK 感知切分函数
  （CJK 游程：长度 1 出单字、≥2 出重叠二元组；非 CJK 游程原样不拆）。
  因为 FTS5 对 `MATCH` 右侧也走分词器，两字查询既不需要引号也不需要特判。
  索引表同时改成 **external-content + `detail=column` + `columnsize=0`**（09 §3）。
- **后果**：①索引**无法原地迁移**（词表不兼容）⇒ 升 `SCHEMA_VERSION` + 后台分批重建（09 §5.4）；
  ②门禁改为**禁止朴素 `ORDER BY rank`**（实测 130-218 ms，必须两阶段有界窗口重排）、
  禁止深 `OFFSET`、`optimize` 只允许用户触发；③回归测试必须包含那四个误报用例。

## D14 通知：Windows App SDK（`已定`）
- **背景**：`tauri-plugin-notification` 桌面端不支持 Actions 与激活路由（A1 分发研究）。
- **结论**：未打包应用用 `Microsoft.Windows.AppNotifications`（`Register()` 自注册），失败回退插件；
  **因此安装必须 `currentUser`**（提权应用不能发通知）。
- **后果**：跳转列表、mailto 注册等也要自己做（17 §9）。

## D15 安装与更新：NSIS currentUser + minisign；**Authenticode 先不买，走免费 OSS 签名**（P3，2026-10-03）
- **背景**：Azure Artifact Signing 个人仅限美/加且无大陆区域；EV 自 2024 起不再免 SmartScreen；
  **公共 CA 不会给个人/OSS 项目免费发代码签名证书**（证书必须签发给法律实体）。
- **用户的约束**：**不花钱而且有效**。
- **结论（三条）**：
  1. **v1.0 不买证书、也不自签**。自签证书对 SmartScreen **无效**（用户照样看到"未知发布者"），
     而且"自签"这个特征本身更像恶意软件 ⇒ **自签比不签更糟**。
  2. **开源的免费正路：SignPath Foundation**（已逐条核对条款，见 `17` §6.2）。条件：OSI 许可、
     无专有组件、活跃维护、**已经发布**、有可验证的**声誉**、团队 MFA、指定 authors/reviewers/approvers、
     首页要有"Code signing policy"页、产物元数据规范；证书签发给 **SignPath Foundation**
     （即"发布者"显示为 SignPath Foundation，不是个人名字）；每次发布需人工批准。
     ⇒ **顺序必然是"先发布 → 攒声誉 → 再申请签名"**，不是开工就能拿到。
  3. **更新链的完整性不依赖 Authenticode**：Tauri updater 的 **minisign 签名**独立生效（D15 原有部分保留），
     所以"不签名"不会削弱自动更新的安全性，只影响首次下载时的 SmartScreen 体验。
- **不签名时怎么把体验做到最好（免费且有效）**：①下载页/README 给"首次运行看到 SmartScreen 怎么办"的
  图文步骤（更多信息 → 仍要运行）；②发布 SHA256 + 一条校验命令；③优先引导用户从 **winget** 安装
  （winget 会校验安装包哈希，路径更"正规"）；④安装包内不放任何会加剧怀疑的东西（无捆绑、无驱动、
  无后台服务）；⑤**若将来开源（P4）**，立刻按 §6.2 申请 SignPath，把"未知发布者"换成基金会签名。
- **后果**：M1 的"能装能更新"不依赖任何花费；"没有签名"这件事要**主动写在文档里**（诚实，
  而不是让用户自己撞上警告）；minisign 私钥仍须离线备份两份（丢失 = 无法再推送更新）。

## D16 规则与垃圾邮件：本地执行（`已定`）
- **背景**：服务端 Sieve 已否决；本地规则可离线生效。
- **结论**：本地规则引擎 + 服务器垃圾判定（`\Junk`）+ 白/黑名单 + 一键退订（One-Click 才自动 POST）。
- **后果**：UI 必须明确"规则只在本机生效"（10 §11 反驳 1）。

## D17 性能基线：10 万封是可验收规模（`已定`）
- **结论**：16 项预算（`15` §4 为唯一权威数字）+ 可重复夹具 + `tools/bench.ps1` + CI 宽松冒烟。
- **后果**：任何新功能都要在预算内；超预算先降级，不许"让用户忍着"。

## D18 PGP 引擎与范围（`待拍板` P8，倾向已定）
- **背景**：sequoia（LGPL，但有 `crypto-cng` 无系统依赖）vs rPGP（MIT/Apache，审计历史较弱）；
  PGP 完整实现 L 级（2-4 个月）。
- **结论（建议）**：引擎用 **rPGP**（许可简单）；范围分两步：v1 做**验签 + 解密 + 密钥管理 + WKD**，
  发送加密后置；不做 Autocrypt（生态弱、策略难）。
- **后果**：解密邮件**永不自动加载远程内容**（efail）；签名状态三态（已验证/未知密钥/警告），灰色不给绿锁。

## D19 日历范围（`待拍板` P7，倾向已定）
- **结论（建议）**：只做"邀请只读 + RSVP + 议程"（覆盖"我要回邀请"这 80% 价值）；
  日/周/月网格与 CalDAV 双向后置（网格是 2-3 个月的前端布局工程，A1-F23）。
- **后果**：`18` 的 `CAL-01/03` 明确标为 M3+。

## D20 无遥测（`已定`）
- **结论**：默认且**没有**开关；出站端点清单可审计（14 §11）+ `NetAudit` 本地台账；
  诊断靠用户手动导出的脱敏诊断包。
- **后果**：质量问题靠用户反馈闭环解决；若将来要做匿名统计，需用户明确同意并解决托管（红线 6）。
