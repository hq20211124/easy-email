## 0. v0.2 是什么（一句话完成定义）

> **版本号口径（2026-10-10 定）**：这一轮按内部叫法叫"v0.2"（README 的进度表一直这么写），
> **发出的 tag 是 `v0.1.2`**。两处版本号手动升，CI 不碰。

**把 M1a「能换过来」收口成一个能发出去的版本：断网时界面自己说、正文搜得到、更新能自己走。**

更严格的三条验收（缺一条就不算 v0.2）：

1. 同步失败时，界面**说清是哪类失败**（离线 / 授权码 / 配额 / 服务器 / 本地），而不是假装在用实时数据；
2. 搜索能命中**已同步但没打开过**的邮件正文，且覆盖率如实显示；
3. Windows 上**能自动更新**（签名校验不可关闭，README 不承诺没有的事）。

## 2. 初稿计划的块清单（5 块 + 发版）

> 初稿是我在"读完 HANDOFF §0.5 的下一步 + README 已知限制"之后直接排的，
> 排序依据是 HANDOFF 自己写的两句："候选里最小最独立的是离线提示；最值钱的是正文全文索引"。

| 块 | 目标 | 主要改动（初稿版） |
|---|---|---|
| **V2-A 正文索引** | 搜索从"只搜已打开的正文"扩展到"已同步的正文" | 同步时顺手把正文存进 `bodies`；FTS 已有（`put_detail` → `refresh_search_row`），前端搜索状态行显示覆盖率 |
| **V2-B 离线提示** | 离线/失败时界面自己说 | 前端读 `sync_status.offline` / `last_error`，列表窗格顶部一条提示 + 重试按钮 |

## 5. 逆向反驳（反向找茬 · 红队，10 条）

> 规则照 `design/README.md` §11：每条给"反驳 → 证据（命令/代码位置）→ 结论或让步"，
> 并且必须做一次**跨文档 + 对代码**的核对。下面每条的证据都是本轮真实跑过的。

### C1 范围：把 M1b 的块提前，却没砍 M1b 的范围

**反驳**：V2-A 名义是"正文索引"一个小功能，实际它属于 `design/19` §4 **M1b** 表首行
「09 搜索与索引（正文 + 附件名 + 可选附件文本、语法、重建）」——那个块的验收是
"10 万封搜索 ≤ 100 ms；索引可重建且可暂停"，规模 2-4 人月的一部分。初稿没写非目标，
执行时必然滑向完整实现。

**证据**：`design/19-roadmap.md` §4 M1b 表；`design/09-search.md` §4 的 `index_queue` 表、
§5 的查询语法与服务器端回退、§11 反驳 2 的三条缓解。

**结论**：**改设计**。V2-A 写成有明确非目标的最小切片：不做 `index_queue`、不做附件文本、
不做索引重建 UI、不做服务器端回退、不换分词器（保留现有逐字切分，HANDOFF §5 已钉死）。

### C2 取件成本被低估一个量级（最严重的一条）

**反驳**：初稿写"同步时顺手把正文存进 `bodies`"，但**现状同步根本不取正文**。
`crates/mail-core/src/imap.rs` 的取件原语只有 `fetch_newest_headers` / `fetch_headers_since` /
`fetch_older_headers`（头部）与 `fetch_message`（整封）。要给"已同步但未打开"的邮件建索引，
只能一封一封 `fetch_message`——**每封的字节量与用户点开它时完全相同**。
窗口默认"最近 2 年"，首启后第一次索引就是几百次取件。

**证据**：

```
$ grep -n "pub async fn" crates/mail-core/src/imap.rs | grep fetch
502:    pub async fn fetch_newest_headers(
565:    pub async fn fetch_headers_since(
622:    pub async fn fetch_older_headers(
678:    pub async fn fetch_message(&mut self, uid: u32) -> Result<MessageDetail> {
778:    pub async fn fetch_message_range(
```

**没写进计划的三个后果**：① 索引任务与 IDLE 泵、手动刷新**抢同一个连接池**
（QQ/网易的 `max_connections` 很严，README 已验证）；② 这些流量算不算进配额账本
（`design/04` §5.7、README 的网易 30 天窗口）？③ 用户看到的是"正在索引"还是静默卡顿？

**结论**：**改设计**。V2-A 从"改同步路径"改为"**后台有界回填**"：
新写一个 pass 语义的索引遍（仿 `worker.rs::run_due` 的 transport 注入 + `limit` 形状），
每遍 20 封、遍与遍之间退避、用户正在操作时不抢连接；覆盖率如实显示，不显示"已完成"的假象。
**同步路径一行不改**——这是本条找茬最重要的产出。

### C3 `offline` 字段名是错的，会把"授权码失效"说成"网络断开"

**反驳**：初稿写"前端读 `sync_status.offline`"。但代码里 `offline` 的语义是
**"上次同步失败"**，与网络无关；而失败可能是授权码失效、服务器拒连、配额到顶
（README 已知限制与 `design/04` §5.7）。把它们全显示成"离线"，
是在用户最需要准确信息的时候给错信息——这比不提示更糟。

**证据**：

```rust
// src-tauri/src/lib.rs:1851
offline: last_error.is_some(),
// src-tauri/src/lib.rs:1886
struct SyncStatus { offline: bool, last_error: Option<String>, ... }
```

另一个初稿没提的事实：`last_sync_error` 只在内存里（`AppState::last_sync_error`，L59），
重启即丢——所以"重启后还显示上次的失败"不会发生，但反过来说**重启后用户看不到任何原因**。

**结论**：**改设计**。V2-B 必须带**结构化失败类型**（`failure_kind`），
在捕获点（`list_messages` 里 `refresh_folder(...).err()`，L577，此时 `MailError` 还在手里、
尚未被 `describe()` 变成字符串）就按 `error.rs` 的变体归类，文案按类型分，
且只在"这次刷新失败"时显示、刷新成功即消失。

### C4 自动更新有 6 件外部/环境前提，初稿一件都没列

**反驳**：初稿把 V2-C 写成一个代码块。实际上：

**证据**（逐条现场核对）：

```
$ grep -n "updater" src-tauri/Cargo.toml src-tauri/tauri.windows.conf.json src-tauri/capabilities/default.json
（无输出）
$ head -12 crates/mail-core/src/update.rs
//! ... Neither the download nor the installer is here (they need an update source and a
//! signing key, which are decisions rather than code) ...
```

1. **签名不可关闭**。Tauri 官方 updater 文档原话："Tauri's updater needs a signature to verify
   that the update is from a trusted source. **This cannot be disabled.**"
   ⇒ 必须由维护者生成 minisign 密钥对（`tauri signer generate -w ~/.tauri/easy-email.key`），
   私钥**永不入库**，只进 GitHub Secrets。这是"人的动作"，不是代码任务。
2. **开配置会让 CI 直接构建失败**：`bundle.createUpdaterArtifacts: true` 而没有
   `TAURI_SIGNING_PRIVATE_KEY` 时 `cargo tauri build` 报错。⇒ **必须密钥先进 Secrets、
   再合配置**，否则每个 tag 的构建全红——这正是"半成品比不做更糟"的实例。
3. **CI 目前不上传 `.sig`、不生成 `latest.json`**（`.github/workflows/release.yml` 只 sha256）。
4. **capabilities 没有 `updater:default`**（`capabilities/default.json` 只有 4 条 core:window）。
5. **插件要求 rustc ≥ 1.90**（官方文档）；本地 1.98/1.99、CI 用 stable，满足，但要记账。
6. **前端没有打包器**：`window.__TAURI__.core` 可用，但 `@tauri-apps/plugin-updater` 的 JS
   不在产物里 ⇒ 下载进度与 rid 包装拿不到，**整条流要放在 Rust 侧做命令**。

**结论**：**改设计 + 拆块**。V2-C 拆成 C1/C2 两个可独立发布的子块（见 C10），
并把"人的动作"单独列成表（见 §7.4）。

### C5 文档对账不是收尾杂务，它现在是"文档在说错话"

**反驳**：初稿把 V2-E 放在最后当"发版杂务"。但 §1 的盘点显示，README 此刻有**三处已经说错**
（附件上限、历史回填、命令数），另有两处仍然正确但即将过时（离线提示、搜索覆盖）。
如果 v0.2 只发代码不改文档，发布说明会和实际行为矛盾——而用户明确要求
"**未验证的事不要写完成**"（HANDOFF §0.5 最后一段）。

**证据**：见 §1 表的 L40 / L692 / L175 / L678 四条，以及 `grep` 输出。

**结论**：**让步**（保留在最后，但升级为发版门禁）。文档对账不单独成为一个"功能块"，
而是拆成两块：① 每块做完**当场**改 README 对应行（不攒着）；
② 发版前过一次 §1 全表（这张表就是机械清单）。

### C6 测试基线数字自相矛盾，而所有"测试没变红"的验收都建立在它上面

**反驳**：`HANDOFF.md` §2 写"351 passed（+7 ignored）"，`PROGRESS.md` M2-1 写"292/293 个测试"。
差 59 个，且两份都没写口径。任何形如"新增 5 个测试、总数为 X"的验收都无法核对。

**证据**：本轮实测 `cargo test --workspace` = 351 passed / 7 ignored，
分解为 5 + 293 + 47 + 4 + 1 + 1（见 §0.1）。**结论：两个数字都对，只是口径不同**
（293 = `mail-core` lib 单测；351 = 全 workspace）。

**结论**：**被说服 + 改方案**。不是"数字错了"，是"没写口径"。
修正稿把口径写进基线（§0.1），并规定：**每块验收只允许用"相对基线 +N，合计 M（附分解）"**，
禁止引用任何不带口径的旧数字。

### C7 块顺序把"等人的事"和"能做的事"混在一张表里

**反驳**：初稿的 V2-E 之后没有区分"等人"与"能做的"。
但 HANDOFF §6/§7 明确列出三件卡在外部条件：Outlook 真机（Azure 账号）、
163/126 真机（网易授权码）、自建服务器真机（一台真服务器）。
若它们进 v0.2 的验收，v0.2 **永远发不出去**。

**证据**：`HANDOFF.md` §6「还没验证的，别以为已经验过」1/2/5 三条；§7 第 ④ 节。

**结论**：**改设计**。发版门禁只有三样：**代码、文档、CI 产物**。
真机三件移入"已实现/未验证"清单，**如实写进 README**，不拦发版。
这与"未验证的事不要写完成"是同一条原则的两面。

### C8 V2-D 会碰到本仓库最魂的一条约束，初稿没提

**反驳**：允许"IMAP 通就保存" = 放松"账号必须是完整的"这条保证。
而 HANDOFF §5 写得很清楚：**校验必须在 `save_account` 里最先做**（写凭据与写
`accounts.json` 之前），"一个改了字段再重试的用户本来就不该创建过它"。
README 已知限制也把"要求 IMAP 与 SMTP 都通"当成现有保证。
若不加约束，表外服务商的半成品账号会变多。

**证据**：`HANDOFF.md` §5「校验必须在 `save_account` 里最先做」；README L708-710。

**结论**：**改设计**。V2-D 的验收必须包含一条：**未勾选「此服务器不提供 SMTP」时，
SMTP 失败仍然拒绝保存**（loopback 夹具测）。勾选是显式 opt-in，不是隐式放宽。

### C9 计划没有"存储/体积"这笔账

**反驳**：正文进 FTS 的直接后果是 `cache.db` 变大。`design/09` §8 给了数字：
10 万封 + 1 年正文 ≈ 800 MB 文本、索引 ≈ 420 MB；§11 反驳 2 的让步是把
`body_index_truncate_bytes` 做成设置项（默认 64 KB）。v0.2 窗口默认"最近 2 年"，
大邮箱的 `cache.db` 会从几百 MB 涨到 GB 级，而 README 一个字都不提。

**证据**：`design/09-search.md` §8 与 §11 反驳 2。

**结论**：**改设计**。V2-A 必须带三件：① **FTS 行内的 body 截断**（默认 64 KB，
存 `user.db` 的 `kv`；**`bodies` 表仍存全文**，因为那是用户要读的正文，截了就是丢数据）；
② 索引覆盖率与体积显示在搜索状态行；③ README 已知限制补一条"正文索引占用多少空间"。

### C10 缺一条"做完就能停"的边界，V2-C 尤其致命

**反驳**：`design/19` §4 要求每个块"不能出现必须一次做完"。
V2-C 中途停下会留下"装了 updater 插件、配了 endpoint，但没有密钥 → 每次检查都失败"的状态；
更糟的是**开了 `createUpdaterArtifacts` 却没密钥 → CI 每 tag 全红**（见 C4-2）。
README 会显示一个永远失败的"检查更新"——这就是半成品。

**证据**：C4 的 6 条前提；`design/19-roadmap.md` §4 表头"可停可续的边界"。

**结论**：**改设计**。V2-C 拆两块：
- **V2-C1（零外部依赖，可立即做、可随时停）**：关于面板显示**当前版本**
  （`env!("CARGO_PKG_VERSION")`）+「打开下载页」按钮（复用 `oauth::SystemBrowser`，
  指向 Releases 页）。**不引插件、不动 CI、不碰密钥。** 用户此刻连"我装的是哪个版本"都看不到，
  这一块本身就有独立价值。
- **V2-C2（需密钥）**：插件 + 配置 + CI + Rust 侧命令 + `update.rs` 记账接线。
  密钥没就绪就先只发 C1；C2 的代码可以先写，但**配置与 CI 改动必须与密钥同一个 PR**。

#### V2-A 正文索引（后台有界回填）

**目标**：搜索命中"已同步但没打开过"的邮件正文；覆盖率如实显示；**同步路径零改动**。

**非目标（照 C1 写死）**：`index_queue` 表、附件文本索引、索引重建 UI、服务器端回退、
换分词器、查询语法扩展。

**改动点**：

| 文件 | 改什么 |
|---|---|
| `crates/mail-core/src/cache.rs` | 新增 `pub fn bodies_pending(&self, account_id: &str, limit: usize) -> Result<Vec<(String, u32)>>`（folder + uid）。SQL 用 `left join bodies ... where b.uid is null ... order by m.date desc, m.uid desc limit ?2`（驱动表是 `messages`，一次查询；不要"取全部 uid 再在 Rust 里筛"） |
| `crates/mail-core/src/cache.rs` | `refresh_search_row` 增加 `body_limit: usize` 参数：**只截断写进 FTS 的 body**（`to_tokens(&body)` 前截到 `body_limit`）；`bodies` 表存全文不动（C9） |
| `crates/mail-core/src/index.rs`（新） | 仿 `worker.rs::run_due` 形状：`BodyIndexRun<'a>`（`cache` / `cfg` / `credential` / `limit`）+ `IndexReport { indexed, failed, remaining }` + `pub async fn index_bodies_pass<F, Fut>(run, fetch: F)`。`fetch` 由调用方注入（loopback 测试给假 transport），失败只记 `failed` 不中断一遍 |
| `crates/mail-core/src/index.rs` | 纯函数 `pick_pending(pending, limit)` + 单测：多于 limit 只取前 limit、按日期新→旧、空列表返回空 |
| `crates/mail-core/src/model.rs` | `SyncStatus` 增 `body_indexed: u32` / `body_pending: u32`（或单独的 `index_coverage` 命令） |
| `src-tauri/src/lib.rs` | 新增命令 `index_coverage(account_id)`；在既有的 worker tick 上挂一个 pass（**用户正在刷新/IDLE 活跃时跳过**，见 C2） |
| `src/app.js` | 搜索状态行补一句覆盖率：「本地已索引正文 x/y 封」；没有 pending 时不显示（全零徽标是装饰不是信息，照 `folder_unread_counts` 的规矩） |
| `tools/check.ps1` | 新增一项：前端读的是覆盖率字段，不是写死的字符串 |

**测试**（至少两层）：
- 单元：`pick_pending` 三态；截断函数（64 KB 边界、中文不被切断半个字——按 char boundary 截）。
- loopback：假服务器 3 封信，第一遍 `limit=2` 只索引 2 封、第二遍索引第 3 封；
  第三封取件失败时 `failed=1` 且前两封的索引仍在。
- 端到端断言：`bodies_pending` 在索引后返回空。

#### V2-B 失败可见性（结构化 `failure_kind`）

**目标**：同步失败时，界面说清是哪类失败；刷新成功即消失；重启后不显示旧失败。

**改动点**：

| 文件 | 改什么 |
|---|---|
| `crates/mail-core/src/error.rs` 或 `src-tauri/src/lib.rs` | 新增纯函数 `pub fn failure_kind(err: &MailError) -> FailureKind`，枚举 `network` / `auth` / `quota` / `server` / `local` / `busy`。映射照 `error.rs` 变体：`Connect`/`Tls` → `network`；`Auth` → `auth`；`Busy` → `busy`；`Cache`/`LocalDb` → `local`；`Imap`/`Smtp`/`Config`/`Credential`/`Parse`/`Timeout` → `server` |
| `src-tauri/src/lib.rs` | `AppState::last_sync_error: Mutex<Option<String>>` → `Mutex<Option<SyncFailure>>`（`{ kind, detail, at }`），在 L577 捕获点赋值（**此时 `MailError` 还在手里**，C3）；`SyncStatus` 增 `failure_kind`、`failed_at`，保留 `offline`（旧字段名保留以不破坏既有调用方，但前端改读 `failure_kind`） |
| `src/app.js` | 列表窗格顶部新增一行 `#sync-banner`（复用 `search-status` 的样式与 `toast` 的色系），文案按 kind 分；「重试」按钮触发当前文件夹刷新；刷新成功后隐藏 |
| `tools/check.ps1` | 新增一项：`src/app.js` 出现 `failure_kind`，且**不再**出现裸 `status.offline` |

**文案（照设计，不临场发挥）**：`network` → "现在连不上服务器，看到的是上次同步的内容。"；
`auth` → "服务器拒绝了登录凭据（授权码可能过期），点重试或重新添加账号。"；
`quota` → "服务商的当日用量到顶了，今天不再同步。";
`local` → "本地数据库出错，收发暂停。";其余 → "同步没成功：{detail}"。

**测试**：单元（`failure_kind` 对每个 `MailError` 变体各一例，含 `Auth` 与 `Connect`）；
前端 gate（上面的 check 项）。

**风险**：`last_sync_error` 是内存态，重启即丢 ⇒ **这是特性不是缺陷**（重启后不该显示旧失败），
README 不用承诺"重启后仍提示"。

#### V2-C2 自动更新（需 minisign 密钥）

**目标**：Windows 上自动检查、下载、重启安装；失败不影响使用；更新没成就说清。

**前置硬条件（C4/C10）**：密钥先生成并进 GitHub Secrets，**与配置改动同一个 PR**。
**平台承诺（2026-10-10 更正，见下）**：四类包各有条目 ——
`windows-x86_64`（NSIS）、`linux-x86_64-deb`、`linux-x86_64-rpm`、`linux-x86_64-appimage`。
依据是 `tauri_plugin_updater::Installer` 的四个 Linux/Windows 变体与 target 串
`{os}-{arch}-{bundle_type}`（docs.rs，2.13.2）。**初稿里"只承诺 Windows"是基于猜测的过度保守，**
**实验证伪**：AppImage 走"整份替换"，不碰 deb/rpm 数据库，互不干扰。

**改动点**：

| 文件 | 改什么 |
|---|---|
| `src-tauri/Cargo.toml` | 加 `tauri-plugin-updater = "2"`（注意 rustc ≥ 1.90） |
| `src-tauri/src/lib.rs` | `plugin` 注册；Rust 侧命令 `check_update() -> Option<UpdateInfo>` / `install_update()`（**进度经 `update:progress` 事件发到前端**，因为前端没有打包器拿不到插件 JS，C4-6）；`on_before_exit` 里写 `UpdateState` 记账（`update.rs` 已备好）；启动时读一次记账，据此显示"已更新到 X"或"更新失败，已回滚到当前版本"+ 一行原因 |
| `src-tauri/tauri.conf.json` + `tauri.windows.conf.json` | `bundle.createUpdaterArtifacts: true`、`plugins.updater.{ pubkey, endpoints, windows.installMode: "passive" }` |
| `src-tauri/capabilities/default.json` | 加 `"updater:default"` |
| `.github/workflows/release.yml` | `windows` job 注入 `TAURI_SIGNING_PRIVATE_KEY` / `_PASSWORD`（secrets）；上传 `.sig`；生成 `latest.json`（version / pub_date / platforms.windows-x86_64.{url,signature}）并上传到 Release |
| `src/app.js` | 「关于」面板显示"有新版 X（点此重启安装）/ 已是最新 / 检查失败（静默，连续 3 次才提示）" |
| `tools/check.ps1` | 新增两项：① `plugins.updater` 段存在且 `pubkey` 是内容不是路径（官方明确"cannot be a file path"）；② `endpoints` 是 https（生产模式强制 TLS） |

**测试**：单元（`update.rs` 记账三态：已更新 / 仍是旧版 / 无记录）；CI 侧用人人可验的一条——
`latest.json` 的 `version` 与 tag 一致（一个 shell 断言，防"忘了升版本号"复发，v0.1.1 犯过）。

**风险与退路**：CI 构建因密钥问题全红 ⇒ 立刻回退该 PR 的配置段，只留 C1；
下载失败 ⇒ 静默 + 重试，绝不阻塞启动（`design/17` §5 状态机）。

#### V2-D 只收信账号（第一个可被砍的块）
